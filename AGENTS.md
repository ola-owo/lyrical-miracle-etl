# Agent Guidelines

## Overview

This is an ETL pipeline that retrieves a user's music listening activity and processes it
for downstream analyses.

## Tech stack

- dagster: pipeline orchestration
- [`dlt`](https://dlthub.com/docs/llms.txt): data extraction, transformation, and loading
- [`neon`](https://neon.com/docs/llms.txt): postgresql database,
  contains dagster run/event metadata
- bigquery: stores ingested data
- `polars` and `pyarrow`: dataframe manipulation
- `scikit-learn`: k-means clustering of lyrics embeddings
- `sqlalchemy` and `psycopg2`: storing/loading pipeline data from postgres
- duckdb: storing/loading data locally when testing
- Gemini Agent Platform: hosts the Big5 model

## Project layout

This is a `uv` Python project with `pyproject.toml` serving as the project manifest.
`data_loader/` contains python code for the main project; each stage is a Dagster asset.
`data_loader/definitions.py` assembles the assets, jobs, and schedule
(`batch_update` weekly, plus on-demand `embed_refresh` and `cluster_all` jobs).

`dagster.yaml`, `Dockerfile`, and `entrypoint.sh` configure the deployment
(single container running the dagster webserver + daemon).

`schemas/` contains data schemas generated by dlt
([as described here](https://dlthub.com/docs/walkthroughs/adjust-a-schema)).

## Testing

Tests live in `tests/` (`pytest` with stdlib `unittest.mock`).
Run them with `uv run --dev pytest`, `pyproject.toml` sets `testpaths = ["tests"]`.

Unit tests are one `test_<module>.py` per module.
Asset-level tests live in `tests/test_assets.py`, asset-check tests in `tests/test_checks.py`,
and definitions smoke tests in `tests/test_definitions.py`.

Tests should never query live services, nor should they depend on the developer's dlt secrets.

### Dagster project integrity

The command `uv run dg check [command]` will validate the Dagster project's integrity.

- Run `uv run dg check defs` after updating Dagster definitions.
- Run `uv run dg check toml` after updating Dagster-related entries in `pyproject.toml`
  or `dg.toml`.
- Run `uv run dg check yaml` after updating `dagster.yaml`.

### Unit tests

Unit tests are for non-asset functions, most of which are wrappers around `dlt` code.

- Use `tests.utils.unwrap` to access the underlying function behind a `dlt.transformer`
  or `dlt.resource`.
- Use `tests.utils.unwrap_check` to access the function behind a `dagster.asset_check`.
- Patch external boundaries at their import site with `monkeypatch.setattr(<module>, ...)`,
  e.g. `sql_table`, `dlt.pipeline`, API clients, or query helpers.
- The autouse `dummy_dlt_config` fixture in `tests/conftest.py` injects dummy dlt
  secrets, so tests run without a local `.dlt/` directory.

### Asset tests

Asset tests are for unit testing Dagster assets.

- Materialize a single asset with `dg.materialize([asset])`.
  Assets are linked only by non-argument `deps`, so no upstream asset runs.
  Partitioned assets need `partition_key=...`.
- Patch `dlt.pipeline` with the `fake_pipelines` fixture and `sql_table` with `fake_sql_table`,
  which record calls instead of loading.
  Set `fake_pipelines.row_counts = {...}` to fake dlt's normalize row counts.
- Inspect what an asset did via `fake_pipelines[0]` (`.args`, `.kwargs`) and its `.pipeline.runs[0]`
  (the `(source, kwargs)` passed to `pipeline.run`).
  Assert the parts the asset controls
  (source/table names, write disposition, primary key, filters, limits), not the mocked internals.
- Asset run config is passed as
  `dg.RunConfig(ops={<ASSET_NAME>: {'config': <RUN_CONFIG>}})`: `ops` is
  `RunConfig`'s first parameter and multi-part asset keys join with `__`.
- Read materialization metadata with
  `result.get_asset_materialization_events()[0].event_specific_data.materialization.metadata`.
- Do not execute implicit jobs (e.g. `defs.get_implicit_global_asset_job_def()`):
  they select every asset and run real externals,
  and `execute_in_process` defaults to `raise_on_error=True`.
  Materialize one asset instead.

### Asset checks

Asset checks are for data quality checks on loaded assets.

- Define checks in `data_loader/checks.py` and register them via `Definitions(asset_checks=...)`,
  attaching each to an `AssetKey`.
  A check runs automatically whenever its asset runs.
- Keep query construction separate from query execution (see `checks._query_count`), so
  tests can patch just the execution with `monkeypatch.setattr(checks, '_query_count', ...)`.
- Assert check registration in `tests/test_definitions.py` via
  `defs.resolve_asset_graph().asset_check_keys` (use `to_user_string()`).
- Check metadata values are dagster wrappers (`IntMetadataValue`); compare `.value`.

## Other guidelines

- When upgrading dagster, check the [release notes](https://github.com/dagster-io/dagster/releases)
  for breaking changes to asset/job APIs.
